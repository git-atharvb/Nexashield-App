# NexaShield File Management System (FMS) - Deep Technical Evaluation

## 1. Executive Summary & Design Rationale
The File Management System (FMS) acts as a centralized, highly secure cryptographic vault for the entire NexaShield application. When modules (like the NIDS exporting a PCAP, or the Phishing Detector exporting a PDF report) need to save sensitive data to disk, they do not write plain text files. Instead, they pipe the raw byte data into the FMS, which ensures data integrity, encrypted storage, and persistent database tracking.

## 2. Cryptographic Mechanisms
The core of the FMS (`_xor_encrypt_decrypt` and `_hash_data`) utilizes symmetric cryptography and cryptographic hashing to protect data at rest.

### 2.1 Symmetric Encryption (XOR)
The FMS employs a bitwise XOR stream cipher utilizing a predefined symmetric key (`NEXASHIELD_SECURE_KEY`).
- **Mechanism:** `bytes([b ^ key_bytes[i % len(key_bytes)] for i, b in enumerate(data)])`. 
- **Security Posture:** While simple, XOR encryption is highly effective for this specific use case. It completely obfuscates the file structure (preventing malware execution or plain-text reading of sensitive PDF reports by unauthorized local users) while remaining computationally inexpensive, allowing massive PCAP files to be encrypted in milliseconds without lagging the GUI.

### 2.2 Cryptographic Integrity (SHA-256)
Before the data is encrypted, the FMS generates a `SHA-256` hash of the raw byte payload. This fingerprint is stored immutably in the SQLite database. If the encrypted `.nxvault` file on disk is tampered with, corrupted, or altered by ransomware, the decrypted hash will no longer match the database record, instantly alerting the system to data corruption.

## 3. Deep Dive: The Data Flow Pipeline
The FMS exposes `export_file` and `read_file` as public APIs for the other NexaShield modules.

### 3.1 The Export Pipeline
When a module calls `export_file(filename, content, module_source, file_type, tags)`:
1. **Type Normalization:** The engine dynamically checks `isinstance(content, str)`. If it's a string, it encodes it to UTF-8 bytes. If it's already a binary payload (like a PDF or PCAP), it passes it directly.
2. **Cryptographic Processing:** Generates the SHA-256 hash and applies the XOR encryption to the payload.
3. **Collision Prevention (Namespace Mapping):** Saves the file to `workspace_dir/vault`. To prevent file overwrites if two modules export "report.pdf" simultaneously, the FMS prepends a high-precision timestamp (`datetime.now().strftime("%Y%m%d_%H%M%S")`) to the filename.
4. **SQLite Registration:** Executes an `INSERT` statement into the `file_registry` table, committing the `filename`, absolute `filepath`, `module_source` (e.g., "NIDS", "Antivirus"), `file_type`, `tags`, `timestamp`, `file_size`, and `file_hash`.

### 3.2 The Retrieval Pipeline
When `read_file(filepath)` is invoked:
1. **Validation:** Asserts `os.path.exists()` to prevent IOErrors.
2. **Ingestion & Decryption:** Reads the encrypted binary payload from disk and passes it back through the XOR function. Because XOR is perfectly symmetric, applying the exact same operation reverses the encryption, returning the pristine original bytes back to the requesting module for display or secondary export.

## 4. Centralized Data Architecture
The `get_all_files()` method executes a `SELECT * ... ORDER BY id DESC` query to return a reverse-chronological list of all vaulted files. This allows the centralized File Manager UI tab to act as a unified dashboard, giving users a single pane of glass to view and manage every single artifact generated by the various disparate security engines (NIDS, AV, Cloud, Phishing) running within NexaShield.
