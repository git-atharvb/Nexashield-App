# NexaShield AI Process Threat Model - Deep Technical Evaluation

## 1. Executive Summary & Core Concept
The NexaShield Processes Module represents a shift from static signature-based detection to dynamic Behavioral Analysis. It employs a localized Machine Learning model (`RandomForestRegressor` via `scikit-learn`) to monitor active system processes in real-time. By continuously evaluating telemetry anomalies, the model identifies sophisticated malware (like fileless malware, cryptominers, and C2 beacons) that easily bypass traditional hash-matching antiviruses.

## 2. Advanced Algorithmic Architecture
The engine relies on a highly tuned Random Forest algorithm.

### 2.1 Why Random Forest Regressor?
- **Non-Linear State Mapping:** Process states do not follow a linear risk trajectory. For instance, high CPU usage is entirely normal for a video game rendering engine, but High CPU + Execution from `AppData` + Active Network Sockets forms a highly anomalous triad. Decision trees natively capture these complex "AND/OR" conditional branches.
- **Noise Resilience:** Operating systems are inherently noisy, with legitimate background tasks frequently spiking resources. Random Forests use ensemble learning (bagging), which effectively smooths out OS-level stochastic noise, drastically reducing False Positives compared to a single decision tree or rigid hardcoded `IF/ELSE` statements.
- **Inference Speed & GIL Optimization:** The `n_jobs` parameter is explicitly forced to 1. While multi-threading ML training is ideal, during real-time inference in a GUI app, spawning multiple C-level threads can cause Global Interpreter Lock (GIL) contention in Python, leading to UI stuttering. A single-threaded Random Forest inference takes `<0.1ms` per process, ensuring 60 FPS UI rendering.

### 2.2 Model Hyperparameters
- `n_estimators`: 100 (Sufficient ensemble size for accuracy without bloating RAM).
- `max_depth`: 10 (Strictly restricted to prevent the model from memorizing synthetic noise and overfitting).

## 3. Deep Feature Engineering & Telemetry Extraction
The model ingests a 7-dimensional feature vector, extracted dynamically via the `psutil` library:

1. **`cpu_percent` (Continuous, 0.0 - 100.0):** Immediate CPU utilization slice.
2. **`memory_percent` (Continuous, 0.0 - 100.0):** Physical RAM footprint ratio.
3. **`thread_count` (Discrete Int):** Number of active parallel execution threads.
4. **`is_system_user` (Binary: 0 or 1):** Validates if the process owner is `NT AUTHORITY\SYSTEM`, `LOCAL SERVICE`, or `NETWORK SERVICE`. Malware running as SYSTEM is exceedingly dangerous.
5. **`is_temp_path` (Binary: 0 or 1) [High-Value Indicator]:** Cross-references the executable path (`exe`) and command-line arguments (`cmdline`) against known temporary directories (`%TEMP%`, `/tmp`). Malware droppers almost universally unpack payloads here.
6. **`is_appdata_path` (Binary: 0 or 1) [Medium-Value Indicator]:** Validates execution from `AppData\Roaming` or `AppData\Local`. While Electron apps use this, ransomware heavily favors it due to write-permissions without UAC elevation.
7. **`has_network` (Binary: 0 or 1):** Scans the process's active socket connections (`psutil.net_connections()`). Essential for detecting Reverse Shells and C2 beacons.

## 4. Dataset Generation & Threat Weighting
Training a behavioral model requires massive data. Since executing 15,000 real malware variants on a dev machine is catastrophic, the model relies on a custom Synthetic Telemetry Generator.

**Dynamic Threat Scoring (Ground Truth Logic):**
- **Base Score:** 0.1 (Benign background noise modeled via Gaussian distributions).
- **Penalties:**
  - Temp Path Execution: `+0.4`
  - AppData Execution: `+0.2`
  - Active Network Sockets: `+0.2`
  - Max CPU Spikes: up to `+0.3`
- **Stochastic Perturbation:** A 5% random variance (noise injection) was applied to the final calculated labels. This ensures the ML model learns generalized relationships rather than perfectly reverse-engineering the exact mathematical formula used to generate the data.

## 5. Threat Level Bucketing (Probability Mapping)
The Regressor outputs a continuous float `[0.0, 1.0]`, which is bucketed for the UI:
- **Level 1 (Safe - Green):** `<= 0.20`. Standard benign activity.
- **Level 2 (Low Risk - Blue):** `<= 0.40`. Slightly elevated (e.g., standard app using network).
- **Level 3 (Moderate - Yellow):** `<= 0.60`. Atypical (e.g., running from AppData with network).
- **Level 4 (High Risk - Orange):** `<= 0.80`. Strong Indicators of Compromise (IoC) (e.g., Temp directory execution).
- **Level 5 (Critical - Red):** `> 0.80`. Immediate threat triad (Temp path + High CPU + Active Network), highly indicative of active ransomware or cryptomining.

## 6. Implementation & UI Integration Architecture
1. **Asynchronous Processing (`QThread`):** The `ProcessWorker` iterates through all system PIDs using `psutil.process_iter()`. It extracts features, handles `AccessDenied` or `ZombieProcess` exceptions gracefully, and pushes vectors through `model.predict()`.
2. **Event Loop Yielding:** To guarantee UI fluidity, the worker yields the GIL (`time.sleep(0.001)`) between every single process evaluation.
3. **Forensics Explainability Engine:** A major challenge in AI is the "Black Box" effect. When a user clicks a flagged process, the Forensics engine reverse-maps the telemetry, dynamically generating human-readable text (e.g., *"This process was flagged as High Risk because it is executing from a Temporary directory while maintaining active network connections"*).
4. **Remediation:** Leverages OS-level commands (`os.kill(pid, signal.SIGTERM)`) integrated directly into the UI to immediately suspend or terminate rogue processes.
